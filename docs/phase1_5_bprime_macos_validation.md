## Timeout and memory gates

[Synthetic evidence](../results/phase1_5_bprime_macos/final_synthetic_verification.json)
records native libc sleep, process exit, partial output, malformed output, explicit
memory-exhaustion reply and wrong namespace. The same nonblocking parent deadline
and kill/reap mechanism terminates the two stalls in 5.002 and 5.005 seconds,
including teardown. The decision deadline stays five seconds; cleanup latency is
reported separately. No Python signal delivery inside native execution is assumed.
The explicit memory-error reply checks failure handling, not kernel enforcement.

Three disposable allocation probes attempted hard/soft
`RLIMIT_AS=536870912` before touched Python, native malloc/memset and anonymous
mmap allocations. On this host each limit request failed with
`ValueError('current limit exceeds maximum limit')`; limits remained unlimited.
Each diagnostic allocation was bounded to 64 MiB and confirmed increased RSS.
Mach `task_info` independently confirms byte-scale resident/peak reporting,
consistent with Darwin ru_maxrss bytes. These are diagnostics, not proof of a
512-MiB cap. No production worker is admitted under this profile.

The adapter rejects successful outputs with reported peaks above 512 MiB, but
post-call rejection cannot prevent transient excess. There is no claim that
periodic monitoring or RSS checks equal Linux's hard address-space enforcement.
No limit was silently relaxed or increased. Native search-node counts remain null.

The initial test harness used `ps` for independent RSS comparison; the sandbox
blocked that command, causing three test failures. Its initial evidence is
[preserved](../results/phase1_5_bprime_macos/synthetic_verification.initial_harness_failure.json).
Replacing that measurement with Mach task_info fixed the harness, not the memory
gate. Final synthetic tests pass while explicitly reporting the hard-cap blocker.

## Minimum prospective amendment and stopping decision

Recommend a separate platform amendment authorizing this exact macOS build/pin,
byte-normalized resource schema, shared five-second parent semantics, restored
path bindings and stored-evidence comparison procedure. Retain every original
scientific document and Linux commitment unchanged. The mathematical C3 definition,
encoding/options, near operations, sampling, lineage, exclusion categories, seeds,
quotas and candidate limits require no change. The tested bytes support eventual
use of the old C3 namespace after review; it is not enabled by this deliverable.

Before production, resolve hard memory enforcement explicitly. Options for review:
(a) demonstrate a macOS kernel-enforced mechanism with the required metric and
ceiling, including startup/shared-memory accounting; or (b) approve a distinctly
weaker monitored/kill plus measured-peak policy, acknowledging overshoot and
changed guarantees. A custom bounded allocator alone is not a whole-process cap.
Neither option is selected/implemented here. A platform amendment cannot describe
post-hoc measurement as equivalent enforcement. Production remains BLOCKED.

No registered candidates, population audit, navigation, fitting, calibration,
selection, assessment, final-held-out execution, historical near-record completion
or inventory sealing occurred. Stop for review of the blocked resource gate and
prospective platform amendment. No return to the Windows machine is required.
